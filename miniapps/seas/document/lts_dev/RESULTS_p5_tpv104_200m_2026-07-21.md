# LTS Phase 5 — TPV104-200m results (jobs 52340525, 52344266, SeisSol 52365078)

**Date:** 2026-07-21 · **Branch:** `safs-v4_0_0-alt-case1-mfem-speed` · **Machine:** SDSC Expanse

## Summary — read this first

**What ran.** The full three-way head-to-head on the SCEC TPV104 200 m production mesh
(2,464,689 tets, md5-verified identical for both codes), 2 nodes, t = 2.0 s, matched Courant 0.5
(both codes computed the identical minimum dt = 366.128 µs — live confirmation the CFL formulas
match): **MFEM GTS**, **MFEM clustered-LTS** (p3/ADER-O4, fault interleave), and
**SeisSol o4 + its own clustered LTS** (job 52365078, binary `v1.3.1-2135` — see §7).

**Scoreboard (stepping rates, all cfl = 0.5):**

| leg | s / sim-s | sim-s / wall-h | vs MFEM GTS |
|---|---:|---:|---:|
| MFEM GTS | 6465 | 0.56 | 1.0× |
| MFEM LTS | 4356 | 0.83 | 1.48× |
| **SeisSol o4 LTS (as-run)** | **239** | **15.1** | **27.1×** |
| SeisSol (compute-only) | 111 | 32.4 | (58×) |

**SeisSol is 18.2× faster than MFEM-LTS as-run — and the dominant cause is NOT the LTS
machinery or the communication. It is a measured 17.1× per-element-update kernel gap at o4:**
MFEM 245.9 µs·core per update vs SeisSol 14.4 µs·core (identical mesh, identical dt, same
order, update counts computed independently for each code). Both codes have the same 3.63×
LTS update-reduction available on this mesh, and both lose a similar ~2.2× to non-compute
overhead (MFEM: exposed `MPI_Waitall`; SeisSol: blocking IO at our matched 0.05 s output
cadence). The order-of-magnitude separation is kernel efficiency.

**This corrects the Phase-0 premise.** The plan's "MFEM 1.354× faster per update (measured)"
was a **p1** measurement. At o4/p3 the measured relation inverts to ~17× in SeisSol's favor —
SeisSol's code-generated batched small-GEMM kernels (~6.4 GFLOP/s/core sustained in its compute
phase) vs MFEM's generic quadrature/DenseMatrix path (~0.4 GFLOP/s/core equivalent). Every
"beat SeisSol at matched order" projection built on the p1 per-update number is void at o4.

**What stands from the earlier analysis.** MFEM's LTS machinery itself is healthy: LTS compute
realizes 3.21× of the 3.68× ceiling (87 %), physics validated at active rupture at np=256, both
cfl. The comm fix (exposed `Waitall` = 53 %) is still real and worth ~2.2× — but it alone gets
MFEM-LTS to ~2015 s/sim-s, still ~8× behind SeisSol's as-run 239. **At matched order, the
decisive lever is now element-kernel efficiency, not scheduling.**

## 2. The kernel gap (the decisive number)

Per-element-update core-time, measured independently on each side:

| | updates in window | core-seconds (compute) | **µs·core / update** |
|---|---:|---:|---:|
| MFEM (GTS leg, pure kernel path, Caliper `step`) | 6.732e9 (t=1.0 s) | 6465 × 256 | **245.9** |
| SeisSol (compute phase 222.3 s, 240 worker cores) | 3.710e9 (t=2.0 s) | 222.3 × 240 | **14.4** |

**Gap = 17.1×.** Supporting detail: SeisSol reports 340.1 TFLOP HW total → ~92 kFLOP per
element update, sustained **6.4 GFLOP/s per core** during compute (~18 % of Rome core peak) via
generated batched small-GEMMs (`computeLocalIntegration` 1153 s, `computeNeighboringIntegration`
1726 s, `computeDynamicRupture` 379 s core-time; load imbalance 6.4 %). If MFEM executes a
comparable FLOP count per update, its effective rate is ~0.4 GFLOP/s/core — i.e. the MFEM p3
ADER path (generic quadrature + DenseMatrix ops, even with `--deriv-cache
--shared-ck-recursion`) is either doing several× the FLOPs or running deeply
memory/latency-bound scalar code. Either way: **the fix is code-generated / batched dense
element kernels, not scheduling.**

## 3. Where each code loses its factor-2 (symmetric, ironically)

| | compute (s/sim-s) | overhead (s/sim-s) | overhead type | total |
|---|---:|---:|---|---:|
| MFEM LTS | 2015 | 2341 | **exposed `MPI_Waitall`** (52.5 % of wall; 17.3 M waits, 585 M msgs) | 4356 |
| SeisSol | 111 | 128 | **blocking IO** (53.5 % of wall; fault+surface writes every 0.05 s, `ASYNC_MODE=SYNC`) | 239 |

- MFEM's overhead is structural (the tick loop's ~125 whole-ghost-layer exchange rounds/sync,
  unoverlapped). GTS on the same mesh: `MPI_Waitall` 0.00002 % — it is purely LTS-loop-induced.
- SeisSol's overhead is *our deck's* output cadence (matched to MFEM's 0.05 s) plus the
  SAFS-proven `ASYNC_MODE=SYNC` setting; with async IO or production cadence SeisSol would run
  close to its 111 s/sim-s compute floor. **The as-run 239 is therefore a conservative
  (favorable-to-MFEM) SeisSol number.** MFEM also carried Caliper instrumentation (~1–3 %) and
  SeisSol sampled PGV every timestep — both second-order.

## 4. MFEM LTS machinery status (unchanged findings, still valid)

- Realized LTS speedup **1.48×** (cfl-invariant: 1.47× at 0.25) vs 3.68× ceiling on this
  near-uniform mesh; **LTS compute alone = 3.21× = 87 % of ceiling** — the element-update
  reduction works; the shortfall is entirely the exposed exchange waits.
- Partition healthy (overall 1.16, fault 2.16, 0 lock violations); GTS balanced to Max/Avg
  1.0000; `Waitall` Max/Avg 1.72 = comm skew, not element imbalance.
- **Physics validated** at np=256 under full rupture, both cfl: V_max peak ~17.3 m/s at
  t ≈ 1.48 s == GTS trace; cfl=0.5 stable (0.25 was inherited conservatism).
- SeisSol physics healthy too: nucleation per matched t_0=1.0 s spec, Mw 6.26 / M0 3.1e18 Nm at
  t=2.0 s, all 6+9 receivers located. Station-level MFEM-vs-SeisSol waveform diff = open item.

## 5. Revised lever ranking (what actually closes the gap)

1. **Element-kernel efficiency (the 17×).** Code-generated / batched small-GEMM ADER kernels
   (libxsmm/PSpaMM-class, or MFEM partial-assembly/`forall` batched tensor kernels adapted to
   the ADER path), memory-layout for contiguous per-cluster batches. Without this, no
   scheduling work can approach SeisSol at matched order. This is the "residual
   kernel-efficiency gap" Phase-0 scoped out — it is now measured at 17× and is the main event.
2. **Comm overlap + exchange-round reduction (the 2.16×).** Still required (any kernel speedup
   makes the exposed-comm fraction *worse*), still concrete (125→32 rounds + cluster-mask +
   overlap → near the compute floor). Do it with or after #1.
3. **The p-drop / low-order angle.** Where MFEM's kernels were competitive (p1) and SeisSol
   cannot follow (compile-time order), the original plan's far-field p-drop strategy remains
   MFEM's structural edge — but the honest framing is accuracy-traded, not matched-order.

## 6. Bottom line

- **MFEM vs itself:** LTS works (1.48× net, 87 % compute realization, physics right at scale).
  The comm fix is real, bounded (~2.2×), and well-attributed.
- **MFEM vs SeisSol at matched order (o4/p3, same mesh, same dt):** SeisSol leads by ~18× as-run
  (~8× even if MFEM's comm were perfectly fixed). The gap is almost entirely per-update kernel
  efficiency (17.1×), which inverts the p1-era Phase-0 premise. Beating SeisSol at matched order
  requires the kernel program; beating it on accuracy-per-cost (p-drop, mixed order) remains the
  alternative axis.
