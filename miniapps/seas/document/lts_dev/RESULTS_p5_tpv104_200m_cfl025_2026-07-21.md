# LTS Phase 5 — TPV104-200m preliminary results (job 52340525)

**Date:** 2026-07-21 · **Branch:** `safs-v4_0_0-alt-case1-mfem-speed` · **Machine:** SDSC Expanse

## Summary — read this first

**What ran.** The clustered-LTS `seas_spatial_dyn_driver` on the SCEC TPV104 200 m
production mesh (2,464,689 tets), p3 / ADER-O4, pure upwind, 256 ranks (2 nodes × 128),
fault-half interleave ON, to t = 2.0 s. Global-timestep (GTS) baseline from the earlier
partner run 52332649.

**Speed.** LTS is **1.47× faster than GTS** on this mesh — against an **ideal ceiling of
3.68×** for this (near-uniform) mesh, i.e. **~40 % of the theoretical LTS gain is realized.**

**Why not more.** Not the partition (well-balanced, 1.16×) and not the global collectives
(`MPI_Allreduce` 0.54 %). **`MPI_Waitall` alone is 53 % of wall time** — the run is
**communication-bound**: the LTS tick loop does ~125 ghost-exchange rounds per sync and the
completion waits sit *exposed* on the critical path instead of overlapping compute.

**Physics.** ✅ **Validated at active rupture** — V_max(t) tracks the GTS trace (peak ~17.3 m/s
at t ≈ 1.48 s), nucleating at t ≈ 1.0–1.1 s and propagating. This is the first at-scale
confirmation of the np>1 fault-half interleave under full rupture (previously only byte-identity
on short local windows).

**Caveat.** All numbers here are at **Courant `cfl = 0.25`**. The **ratio (1.47×) and the
Caliper attribution are cfl-independent** and stand. Absolute `sim-s/wall-h` must be ×2 for the
SeisSol head-to-head; the matched `cfl = 0.5` rerun is pending (decks committed at `56539cc`).

## 3. Caliper attribution — the bottleneck

Per-region wall (256 ranks, whole run):

| region | Time % | Avg s/rank | Max s/rank | Max/Avg | calls (total) |
|---|---:|---:|---:|---:|---:|
| **`MPI_Waitall`** | **52.997 %** | 9216 | 15800 | **1.71** | 34.7 M |
| `MPI_Allreduce` | 0.540 % | 93.9 | 141.9 | 1.51 | 157 k |
| `MPI_Isend` | 0.081 % | 14.1 | 21.2 | 1.50 | **1.17 B** |
| `MPI_Comm_dup` | 0.070 % | 12.2 | 14.6 | — | 256 |
| `MPI_Irecv` | 0.023 % | 4.1 | 7.8 | 1.92 | **1.17 B** |
| everything else MPI | < 0.01 % each | — | — | — | — |
| *(un-annotated compute)* | *~46 %* | — | — | — | — |

**Reading it:**
- **`MPI_Waitall` = 53 % of wall.** Over half the run is spent *waiting for ghost-exchange
  completion*. The point-to-point injection (`Isend`/`Irecv`) is cheap (< 0.11 % combined) — the
  cost is the **blocking wait**, i.e. the exchange is on the critical path and does **not**
  overlap compute.
- **Collectives are negligible** (`Allreduce` 0.54 %, everything else < 0.01 %). The matched-
  collective tick contract is not the problem.
- **1.17 billion point-to-point messages** (4.57 M/rank, ~8400 per rank per sync) — latency-bound
  many-small-messages pattern; ~250 `Waitall` per rank per sync ≈ 2× the ~125 predict+correct
  exchange rounds.
- **`Waitall` Max/Avg = 1.71** — real *wait-time* imbalance on top of a balanced *partition*
  (1.16). Some ranks idle 1.7× the average at the tick barriers. This is communication/
  synchronization skew, not element-count imbalance.

**Diagnosis: the run is communication-bound.** Compute ~46 %, exposed communication ~54 %
(dominated by exchange-completion waits). A well-overlapped LTS keeps comm hidden behind compute
(near-zero exposed wait); here it is fully exposed and serialized with compute by the tick
dependency chain.

## 5. Next levers (ranked by the attribution)

The 40 % realization is a **communication** problem, and the fix path is concrete:

1. **Reduce exchange rounds (biggest win).** The tick loop exchanges per predict *and* per
   correct for every cluster (~125 rounds/sync). Merge into **per-tick** exchanges (125 → 32) and
   **cluster-mask** them (exchange only the clusters active at each tick, not the whole ghost
   layer). Cuts the message/wait count ~4×.
2. **Overlap comm with compute.** Post the ghost exchange *before* the independent compute so
   `MPI_Waitall` overlaps instead of blocking — SeisSol's communication-thread model. Even with
   the current round count, perfect overlap would take wall from ~100 % to ~max(46 % compute,
   54 % comm) = 54 %, i.e. ~2.7× realized.
3. **Aggregate messages.** 1.17 B messages is latency-bound; coalesce per-face into per-neighbor-
   rank sends (fewer, larger messages).

**Projected payoff.** Reduce rounds ~4× (comm ~54 % → ~14 %) *and* overlap → wall approaches the
compute floor (~46 %): realized speedup ~1.48 / 0.46 ≈ **3.2×**, i.e. **~85 % realization** — near
the 3.68× ceiling. That is the Phase-6 (perf) work; this run is the measurement that motivates it.
