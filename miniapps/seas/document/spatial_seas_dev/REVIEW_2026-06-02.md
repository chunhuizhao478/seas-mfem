## Findings

### [R-007] CRITICAL [Phase 3 acceptance + Phase 5 §B + Phase 7 — BP5 prestress reproducibility] — The planned `FaultLocalPrestress` mechanism cannot reproduce BP5's spatially-heterogeneous analytic prestress, so the Phase-3 parity test and the Phase-7 validation gate are unsatisfiable as written

**Category:** BUG (acceptance criterion / validation strategy is structurally unachievable)

**Description:**
The whole plan is gated on BP5 parity (decision **C**, Phase 7). Two acceptance criteria assume the spatial
`[stress]` path can reproduce the **analytic** BP5 per-DOF prestress `tau_pre_` and effective normal stress
`sigma_n_per_dof_`:

- **Phase 3** (plan line 359): build `FaultGeometry` two ways and assert `a_values_, dc_values_,
  eta_values_, **tau_pre_, sigma_n_per_dof_**, V_init_vec_` agree element-wise to `1e-10`, where path (a) is
  the analytic ctor `(domain, params, &mpi)` and path (b) is `(domain, seed, &mpi, false)` + `SetRateStatePerDOF`
  + `ComputeParams*`.
- **Phase 7** (plan lines 496, 500-502): a BP5 TOML with `[stress] FaultLocalPrestress (BP5 τ0/σ_n)`, and
  station traces must match `seas_driver.cpp` to golden tolerance.

Both are impossible with the planned mechanism, for two concrete reasons verified in source:

1. **`sigma_n_per_dof_` is never populated by path (a).** `ComputeBP5Params` (`fault_geometry.hpp:1391`)
   fills only `a_values_/eta_values_/dc_values_/tau_pre_/V_init_vec_` — it **never writes `sigma_n_per_dof_`**
   (the only writers are `ComputeParamsFaultLocal` :685-691 and the sidecar projection). So in path (a)
   `sigma_n_per_dof_` has size 0, while path (b)'s `ComputeParamsFaultLocal` makes it size `N`. The
   element-wise `1e-10` comparison of `sigma_n_per_dof_` is **ill-posed** (size-0 vs size-N).

2. **BP5 `tau_pre_` is strongly spatially heterogeneous; `FaultLocalPrestress` is uniform.** The analytic
   prestress (`config/bp5_params.hpp:333` `tau0_vec`) is
   `tau0 = σ_n·a(x2,x3)·asinh(V_init(x2,x3)/(2V0)·e^{ψ_ss/a(x2,x3)}) + η·|V_init(x2,x3)|` **plus** a
   nucleation-zone `delta_tau` taper. It varies per DOF because `a_of_x2_x3` differs between the VW core
   (a≈0.004) and VS borders (a≈0.04) and because the nucleation patch adds `delta_tau`. The plan's path
   writes it via `geom.ComputeParamsFaultLocal(tau_strike, tau_dip, σ_n, P_p)` (Phase 5 line 423), which
   sets the **same scalar** `tau_dip`/`tau_strike` on every DOF (`fault_geometry.hpp:689-690`). A uniform
   field cannot equal an `a(x)`-dependent field with a localized nucleation bump.

3. **No stress-source kind computes the rate-state steady-state prestress.** Verified the available kinds
   (`spatial_stress.hpp` + `spatial_dyn_driver.cpp:1337-1458`): `ConstantTensor` (uniform tensor),
   `FaultLocalPrestress` (uniform scalars), `DepthProportionalToShearModulus` (depth-only), `SidecarHDF5`
   (per-DOF, externally supplied). None evaluates the BP5 `tau0_vec` formula. The resolver does **not** help:
   `RateStatePerDOFParams` (`spatial_friction.hpp:687`) carries `a,b,Dc,V_init,f_0,V_0,eta,sigma_n_eff` but
   **no prestress** — `ResolveRateState` never produces `tau_pre`.

Net effect: path (b) ≠ path (a) on `tau_pre_` and `sigma_n_per_dof_`, so the Phase-3 parity assertion fails;
and the spatial BP5 run has a uniform prestress where `seas_driver.cpp` has an `a(z)`-varying one, so the
Phase-7 station traces diverge from the golden. The implementing agent will spend the whole effort up to the
gate before discovering the gate cannot pass.

**Trigger:** Implementing Phase 3 / Phase 7 exactly as written and running the parity assertions on the BP5
mesh (any rank count; the heterogeneity is in `a(z)`, not the partition).

**Actual behavior (as planned):** Phase-3 `sigma_n_per_dof_` comparison aborts/under-defined (size mismatch);
`tau_pre_` comparison fails (uniform vs heterogeneous). Phase-7 BP5 station traces do not match the golden.

**Expected behavior:** A path that reproduces BP5's analytic, spatially-varying steady-state prestress per DOF.

**Suggested fix (plan §Phase 3 acceptance, §Phase 5 §B, §Phase 7 — choose one and write it normatively):**
```diff
 ### Phase 3 acceptance — parity test
-- [ ] ... build FaultGeometry two ways — (a) analytic BP5 ctor; (b) new path + SetRateStatePerDOF + ComputeParams*
--     ... assert a_values_, dc_values_, eta_values_, tau_pre_, sigma_n_per_dof_, V_init_vec_ agree to 1e-10.
+- [ ] Split the parity assertion by who populates each array:
+      * a_values_, dc_values_, eta_values_, V_init_vec_  : compare path(a) ComputeBP5Params vs
+        path(b) SetRateStatePerDOF(rs) — the resolver path MUST reproduce these to 1e-10.
+      * tau_pre_, sigma_n_per_dof_                        : ComputeBP5Params does NOT populate
+        sigma_n_per_dof_ and produces a SPATIALLY-VARYING tau_pre_ (bp5_params.hpp:333: a(z)-dependent +
+        nucleation delta_tau).  Reproducing it requires a per-DOF prestress source, NOT uniform
+        FaultLocalPrestress.  Either (i) drive both paths through the SAME per-DOF prestress (e.g. a
+        precomputed BP5 tau0 SidecarHDF5, or a new BP5-analytic stress source) and compare, or (ii) compare
+        tau_pre_/sigma_n_per_dof_ against the analytic bp5_params.tau0_vec/sigma_n directly.
```
```diff
 ### Phase 7 — BP5 verification TOML
-`[stress]` `FaultLocalPrestress` (BP5 τ0/σ_n)
+`[stress]` must reproduce BP5's spatially-varying steady-state prestress (a(z)-dependent + nucleation Δτ),
+which uniform FaultLocalPrestress CANNOT do.  Generate a per-DOF BP5 tau0/σ_n SidecarHDF5 (evaluate
+bp5_params::tau0_vec on the owned fault DOFs) OR add a `bp5_analytic` stress source that calls the same
+formula.  Document that FaultLocalPrestress (uniform) is only valid for problems with uniform prestress.
```
(Also note for the parity setup: BP5 `eta` is auto-computed from material μ/c_s when `eta_auto` is set
(`spatial_friction.cpp:2024`), whereas path (a) uses `seed`'s μ/c_s — the test's `MaterialField` μ/c_s must
equal the BP5 `seed` values or `eta_values_` parity also fails.)

### [R-008] MODERATE [Phase 1 line 205 vs Phase 2 line 236 — `ParseQDSolverType` return type] — Function declared to return `std::string` but used as a `SolverType` enum constructor argument → will not compile

**Description:**

### [R-009] MODERATE [Phase 6 line 475 — checkpoint reuse] — Reusing `io/tpv104_checkpoint.hpp` violates the plan's own no-dynamic-dependency constraint and its `Q`+`DOFData` schema does not fit the QD state

**Category:** BUG (plan self-contradiction + schema mismatch)

**Description:**
Phase 6 (plan line 475) says: "persist `(t, dt, step, state, dof_data-equivalent)` via `io/tpv104_checkpoint.hpp`
with a new `driver_tag="spatial_seas"`. The QD checkpoint stores the **fault state vector**
(`[s_dip,s_strike,psi]*N_owned`) … **not** a bulk `Q`."

But `io/tpv104_checkpoint.hpp`:
- **`#include "../dynamic/fault_face_flux.hpp"  // DOFData`** (`tpv104_checkpoint.hpp:40`) and its entire API is
  built around `const std::vector<DOFData> &dof_data` and a bulk `const Vector &Q`
  (`WriteTpv104Checkpoint(..., const Vector &Q, const std::vector<DOFData>&, ..., driver_tag)` :74-77;
  `ReadTpv104Checkpoint(..., Vector &Q, int expected_Q_size, std::vector<DOFData>&, ...)` :147-150).

This directly contradicts the plan's **§Constraints** "No dynamic-code dependency" rule (plan line 154): the
spatial_seas driver must **not** `#include dynamic/fault_face_flux.*` nor use `DOFData`. Reusing this header
pulls both in transitively.

Separately, the schema does not fit: the QD state is a flat `[s_dip,s_strike,psi]*N_owned` `Vector`, there is
**no** bulk `Q` (the plan says so itself), and the per-DOF dynamic record is a `DOFData` (impedances,
corrected tractions, etc.) that the QD operator does not have. The `driver_tag` trailer mechanism exists, but
it only tags the file — it does not relax the `Q`+`DOFData` payload requirement.

**Trigger:** Implementing Phase 6 by `#include`ing `io/tpv104_checkpoint.hpp` in `spatial_seas_driver.cpp`.

**Actual behavior:** Build couples the QD driver to dynamic/wave code (constraint violation, and project memory
`[1]`/`[C2]` keeps `dynamic/fault_face_flux.*` off-limits as a dependency for the QD driver); and the
`Q`/`DOFData` call signature cannot represent the QD state without fabricating empty `Q` and a `DOFData`
shoehorn.

**Expected behavior:** A QD-native checkpoint that serializes the flat state vector + per-DOF static params
with no dynamic-code dependency.

**Suggested fix (plan Phase 6 line 475):**
```diff
-  - **Checkpoint/restart**: persist `(t, dt, step, state, dof_data-equivalent)` via `io/tpv104_checkpoint.hpp`
-    with a new `driver_tag="spatial_seas"`. The QD checkpoint stores the **fault state vector** ... not a bulk `Q`.
+  - **Checkpoint/restart**: add a QD-native checkpoint (e.g. `io/seas_qd_checkpoint.hpp`) that serializes
+    `(t, dt, step)` + the flat fault state `Vector` (`[s_dip,s_strike,psi]*N_owned`) + per-DOF static params,
+    with a `driver_tag="spatial_seas"` trailer.  Do NOT reuse `io/tpv104_checkpoint.hpp`: it `#include`s
+    `dynamic/fault_face_flux.hpp` (DOFData) and is `Q`+`DOFData`-centric, which violates §Constraints
+    "No dynamic-code dependency" and does not match the QD state layout.  (May copy the v2.2/MPI-rank framing
+    + DRIVER_TAG_V1 trailer logic, but not the header itself.)
```

### [R-010] MODERATE [Phase 3 line 300 — `SetRateStatePerDOF` V_init expansion] — Instruction to expand `rs.V_init` "consistent with `tau_pre_`" is temporally impossible (tau_pre_ is NaN at that point) and leaves the dip/strike direction unspecified

**Category:** ASSUMPTION / BUG (unsatisfiable spec → wrong initial slip-rate risk)

**Description:**
Phase 3 (plan line 300) specifies `SetRateStatePerDOF` must fill `V_init_vec_` by "expanding `rs.V_init` into
the `[2N]` dip/strike interleave **consistent with `tau_pre_`**". Two problems, both verified:

1. **`rs.V_init` is a size-`N` scalar magnitude**, not a direction: `ResolveRateState` sets
   `p.V_init.SetSize(N)` and writes one value per DOF (`spatial_friction.cpp:1941, 2079`). The operator
   requires `V_init_vec_` of size `2N` and asserts it (`rate_state_fault.hpp:161`:
   `V_init.Size() == 2*num_nodes_`). So a magnitude→(dip,strike) split is mandatory, and `rs` carries no
   direction to base it on.

2. **`tau_pre_` does not exist when `SetRateStatePerDOF` runs.** Per the (correct, R-001) order,
   `SetRateStatePerDOF` runs in Phase 3 **before** the fault-op ctor and **before** `ComputeParamsFaultLocal`
   (Phase 5 §B), which is the only thing that populates `tau_pre_`. At Phase-3 time the
   `compute_bp5_params=false` ctor has NaN-filled `tau_pre_` (`fault_geometry.hpp:286-287`). So "consistent
   with `tau_pre_`" references **NaN data** — the rule is unsatisfiable as written.

Because the direction is left undefined, the implementer must invent it. If they guess wrong (e.g. put the
magnitude in the dip slot, or split it across both), the initial slip-rate direction is wrong, which feeds the
4-phase init (`SetInitialCondition`) and the equilibrium check — exactly the class of sign/frame error
`CLAUDE.md` warns causes positive-feedback blowup. (For comparison, the analytic path's `V_init_vec`
(`bp5_params.hpp:279`) writes a definite `(Vi[0]=dip, Vi[1]=strike)` 2-vector; the spatial path must match
*that* convention, sourced from the loading/initial-velocity direction, not from `tau_pre_`.)

**Trigger:** Implementing `SetRateStatePerDOF` per the Phase-3 instruction.

**Actual behavior:** No well-defined expansion; "consistent with tau_pre_" reads NaN. Implementer-dependent
direction → possible wrong initial slip-rate.

**Expected behavior:** Specify the magnitude→(dip,strike) split explicitly, sourced from the prescribed
initial-velocity / plate-loading direction (matching `bp5_params::V_init_vec`'s convention), independent of
`tau_pre_`.

**Suggested fix (plan Phase 3 line 300 + Architecture line 124):**
```diff
-  - `void SetRateStatePerDOF(const spatial::RateStatePerDOFParams& rs);` — fills `a_values_`, `dc_values_`,
-    `eta_values_`, and `V_init_vec_` (expanding `rs.V_init` into the `[2N]` dip/strike interleave consistent
-    with `tau_pre_`), and `sigma_n_per_dof_` from `rs.sigma_n_eff` ...
+  - `void SetRateStatePerDOF(const spatial::RateStatePerDOFParams& rs, const Vector& init_vel_dir /*2N or {dip,strike} unit dir*/);`
+    — fills `a_values_`, `dc_values_`, `eta_values_`, and `V_init_vec_` by decomposing the size-N magnitude
+    `rs.V_init(i)` along the prescribed initial-velocity direction (dip,strike), matching the convention of
+    `bp5_params::V_init_vec` (V_init_vec_(2i)=dip, V_init_vec_(2i+1)=strike).  Do NOT reference `tau_pre_`:
+    it is unpopulated (NaN) until ComputeParamsFaultLocal runs in Phase 5, after this call (R-001 order).
+    `sigma_n_per_dof_` from `rs.sigma_n_eff` if not already set.
```

**Test case:**
```cpp

}
```
