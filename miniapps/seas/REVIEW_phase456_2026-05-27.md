### [R-001] MODERATE [DEVIATION] [spatial/code/spatial_friction.cpp:parse_spatial_rule + ResolveSlipWeakening/resolve_rs_impl] — `boxcar_taper` rule is parsed but never applied as a taper; `cohesion_inner`/`cohesion_outer` are dead fields and the rule silently acts as a hard region

**Category:** DEVIATION

**Description:**
Phase 6 req 5 adds the `BoxcarTaper` rule kind, `SCECBoxcar`, `BoxcarTaperFactor`,
and the `cohesion_inner`/`cohesion_outer` taper endpoints. The taper helper and
fields exist and round-trip, but **nothing consumes them**:
- `cohesion_inner` / `cohesion_outer` are written only by the parser
  (`spatial_friction.cpp:530-531`); `grep` shows zero readers in any `.cpp/.hpp/.inl`.
- `BoxcarTaperFactor(x,y,z)` is used only inside `matches()` as `> 0.0`
  (`spatial_friction.cpp:106`); it never scales a resolved parameter.
- Both resolvers iterate `cfg.spatial` and, for any rule whose `matches()` is
  true, apply the rule's **hard** overrides (`r.mu_s/mu_d/d_c/cohesion`, LSW
  `:1585-1588`; `r.a/b/Dc/...`, RS `:1699+`). For a `BoxcarTaper` rule
  `matches()` returns `BoxcarTaperFactor(...) > 0`, i.e. true across the plateau
  **and the entire tanh transition zone**. So the transition zone receives the
  *same* value as the plateau — there is no taper at all.

Net effect: a user who writes a `boxcar_taper` rule to get a smooth cohesion
ramp (the documented purpose) gets either (a) **no effect** if only
`cohesion_inner`/`cohesion_outer` are set (both dead → resolved cohesion stays
at the block default), or (b) a **hard region** with a sharp edge if `cohesion`
/`mu_s`/`d_c` are set instead (applied uniformly over the whole boxcar+transition
footprint). Both silently contradict the feature's intent.

This is inconsistent with req 6, where the new nucleation kinds are explicitly
documented as "config-only; the resolver/applicator is Phase 7" and are gated by
a `NucleationKind` dispatch so they cannot be silently mis-consumed. The
`boxcar_taper` rule flows through the *same* resolver loop as `box`/`depth` and
is silently mis-consumed.

**Trigger:**
Any `[[friction.slip_weakening.spatial]]` (or `...rate_state.spatial`) rule with
`kind="boxcar_taper"`, parsed then passed through `ResolveSlipWeakening` /
`ResolveRateState`. (No current SAFS TOML uses it, so no live run is wrong yet;
it becomes wrong the moment a TPV TOML adopts it — e.g. TPV205 surface cohesion
taper in Phase 8.)

**Actual behavior:**
`cohesion_inner`/`cohesion_outer` are ignored; `BoxcarTaperFactor` is used only
as a 0/non-0 region test, so the resolved per-DOF parameters do not taper.

**Expected behavior:**
Either (preferred) the resolver blends the taper endpoints by the factor —
`cohesion(i) = cohesion_outer + (cohesion_inner − cohesion_outer)·BoxcarTaperFactor(x,y,z)`
— for `BoxcarTaper` rules; or, if taper consumption is genuinely deferred to a
later phase, the parser/resolver must **explicitly reject or skip**
`boxcar_taper` rules (as req 6 gates the nucleation kinds) so they cannot be
silently mis-applied, and the deferral must be documented in the header next to
the fields (as req 6 documents its specs).

**Suggested fix:**
Honor the taper in both resolvers. In `ResolveSlipWeakening`
(`spatial_friction.cpp:1573-1589`), special-case the taper kind before the
generic hard-override block:
```diff
       for (const auto& r : cfg.spatial)
       {
          if (!r.matches(x, y, z, dof_to_attr[i])) { continue; }
          if (r.kind == SpatialRule::Kind::Barrier)
          {
             mu_s_i = 1.0e6;
             continue;
          }
+         if (r.kind == SpatialRule::Kind::BoxcarTaper)
+         {
+            // Smooth cohesion taper: blend inner<->outer by the boxcar factor.
+            // Falls back to the block default for any unset (NaN) endpoint.
+            const real_t F = r.BoxcarTaperFactor(x, y, z);
+            const real_t c_in  = std::isnan(r.cohesion_inner) ? coh_i : r.cohesion_inner;
+            const real_t c_out = std::isnan(r.cohesion_outer) ? coh_i : r.cohesion_outer;
+            coh_i = c_out + (c_in - c_out) * F;
+            // mu_s/mu_d/d_c may also be tapered the same way if set; otherwise
+            // a boxcar_taper rule does not touch them.
+            continue;
+         }
          if (!std::isnan(r.mu_s))     { mu_s_i = r.mu_s; }
          if (!std::isnan(r.mu_d))     { mu_d_i = r.mu_d; }
          if (!std::isnan(r.d_c))      { d_c_i  = r.d_c; }
          if (!std::isnan(r.cohesion)) { coh_i  = r.cohesion; }
       }
```
(Apply the analogous `continue`-after-taper handling in `resolve_rs_impl`, or —
if RS taper is out of scope now — `MFEM_VERIFY(r.kind != SpatialRule::Kind::BoxcarTaper, ...)`
in the RS loop with a "not yet supported on the RS path" message.)
If instead the team chooses to defer: add at parse time
`MFEM_VERIFY(out.kind != SpatialRule::Kind::BoxcarTaper, "boxcar_taper is config-only in Phase 6; resolver wiring lands in Phase <N>")`
and remove the "matches → hard region" trap.

**Test case:**
```cpp

// LSW rule must produce a SMOOTH cohesion between cohesion_outer and
// cohesion_inner across the transition zone — not a constant/default value.
static void test_R001_boxcar_taper_cohesion_actually_tapers()

      + "[[friction.slip_weakening.spatial]]\n"
        "kind=\"boxcar_taper\"\n"

        "cohesion_inner=1.0e6\ncohesion_outer=0.0\n";
   const auto cfg = ParseSpatialFrictionConfigString(toml);
   // 3 DOFs: plateau (z=-7500), mid-transition (z=-11250), far outside (z=-20000)
   mfem::Vector coords(9);
   coords = 0.0; coords(2) = -7500.0; coords(5) = -11250.0; coords(8) = -20000.0;
   mfem::Array<int> attr(3); attr = 1;
```

### [R-003] LOW [EDGE_CASE] [spatial/code/spatial_friction.cpp:parse_root `[fault_geometry]` guard] — unit-norm tolerance 1e-9 rejects legitimately hand-entered (slightly-rounded) direction vectors

**Category:** EDGE_CASE

**Description:**
The `[fault_geometry]` guard requires `|ref_normal| - 1` and `|up| - 1` within
`1e-9`. That tolerance is far tighter than a human typically types a normalized
vector. A dipping-fault normal entered as `ref_normal=[0.577,0.577,0.577]`
(intending `1/√3 ≈ 0.57735`) has norm `0.999393`, off by `6.07e-4` ≫ `1e-9`, and
is **rejected** — the user must type ~10 significant digits. The default
axis-aligned vectors are exact, so this only bites non-axis-aligned (TPV31-style
dipping) configs, but it will surface there.

**Trigger:** `[fault_geometry] ref_normal=[0.577,0.577,0.577]` (or any hand-rounded
unit vector).

**Actual behavior:** Aborts "ref_normal must be unit-norm".

**Expected behavior:** Accept vectors that are unit-norm to a human-reasonable
tolerance (and/or normalize internally), reserving the abort for clearly-non-unit
input (typos, zero vectors).

**Suggested fix:**
```diff
-      MFEM_VERIFY(std::abs(nn - 1.0) <= 1e-9,
+      MFEM_VERIFY(std::abs(nn - 1.0) <= 1e-6,
                   "[fault_geometry].ref_normal must be unit-norm; |ref_normal| = "
                   << nn);
-      MFEM_VERIFY(std::abs(un - 1.0) <= 1e-9,
+      MFEM_VERIFY(std::abs(un - 1.0) <= 1e-6,
                   "[fault_geometry].up must be unit-norm; |up| = " << un);
```
(1e-6 still rejects `[0.577,…]`'s 6e-4 error, so prefer this companion: normalize
in place after a looser sanity check, e.g. require `nn > 0.9 && nn < 1.1` then
divide `ref_normal`/`up` by their norms before storing. Pick one approach; do not
ship the current 1e-9 if dipping-fault configs are expected.)

**Test case:**
```cpp
static void test_R003_fault_geometry_rounded_unit_vector_accepted()
{
   const std::string toml = MinimalLSWHeader() + MinimalLSWBlock()
      + "[fault_geometry]\nref_normal=[0.5773502692,0.5773502692,0.5773502692]\n"
        "up=[0.0,0.0,1.0]\n";
   // With normalize-on-read (or >=1e-6 tol + a properly-normalized triple)
   // this must NOT abort; today a 6-dp rounding like [0.577,0.577,0.577] does.
   const auto cfg = ParseSpatialFrictionConfigString(toml);
   TEST_ASSERT(cfg.schema_version == 1, "rounded unit normal accepted");
}
```

  the plan (req-5 scope clarification) document the deferral + justification.
  The kind + `SCECBoxcar`/`BoxcarTaperFactor` still parse and are unit-tested.
  New tests: `test_spatial_friction_resolver` `B-3` (LSW reject) + `R-11` (RS
  reject) — both fail without the guard.  `boxcar_taper` parse/factor coverage
  (`BOX-1..4`) unchanged and still green.
